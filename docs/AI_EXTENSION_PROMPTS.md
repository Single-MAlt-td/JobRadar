# Extending JobRadar with AI

JobRadar is 100% vibe-coded, so using a coding AI to extend it is a natural workflow.

This page contains reusable starting prompts. Adapt them to your coding AI and the task.

---

# General workflow

1. Create a Git feature branch (see [CONTRIBUTING.md](CONTRIBUTING.md)).
2. Make a ZIP containing only the relevant source files (⚠️ see the warning below!).
3. Give the ZIP to a coding AI.
4. Describe the desired behavior precisely and ask to preserve unrelated behavior (see [Prompt examples](#prompt-examples)).
5. Test the generated result.
6. Write a detailed commit message (or let the AI generate it) and commit the changes.
7. Push it to your fork/branch.
8. Open a pull request if the feature is generally useful.


> ⚠️ **Before uploading a ZIP, inspect it manually. Never include your JobRadar database or secrets.**

The ZIP should **NOT** contain the following:

```text
jobradar.db
*.db
*.sqlite
.env
API keys
personal AI profiles
private exports
application records
logs containing private data
.venv/
__pycache__/
build/
dist/
```

# Prompt examples

## Prompt for adding another AI provider

```text
Please extend this Python/Tkinter application called JobRadar.

The attached source code already supports OpenAI, Mistral and Ollama.
Please inspect the existing provider abstraction and add support for <PROVIDER>.

Requirements:
- Preserve all existing provider behavior.
- Follow the existing provider interface instead of duplicating AI logic.
- Add the provider to the Settings UI.
- Support API-key configuration in the same style as existing providers.
- Support Screening, Deep Screening and job-description reformatting where the provider is compatible.
- Keep structured-output handling compatible with the existing application.
- Add clear error handling for authentication errors, rate limits, timeouts and malformed responses.
- Do not hard-code API keys.
- Do not modify unrelated GUI or database behavior.
- List every changed file and briefly explain each change.

Before modifying code, summarize the current AI architecture and identify the minimum set of files that must change.
```

## Prompt for adding another Company Watch adapter

```text
Please extend JobRadar's Company Watch feature.

The attached code already contains adapters for several career systems.
Please add support for <CAREER SYSTEM>.

Use the existing adapter architecture and normalized job representation.

Requirements:
- Detect the platform automatically when possible.
- Retrieve all currently open jobs.
- Support pagination.
- Use stable source job IDs.
- Retrieve title, company, description, URL and all available locations.
- Preserve multiple locations instead of flattening them into one string.
- Support the existing country filter where possible.
- Fail gracefully if the website/API structure differs.
- Integrate with the existing career-source diagnostic output.
- Do not break existing adapters.
- Do not rewrite unrelated code.

I will provide:
1. the current relevant JobRadar source files,
2. one or more example career URLs,
3. diagnostic JSON files generated by JobRadar.

First analyze the examples and existing adapter interface, then propose the smallest robust implementation.
```

## Prompt for updating a broken external API

```text
JobRadar's integration with <SERVICE> has stopped working.

I will provide:
- the current importer/adapter code,
- the exact current error message,
- one or more current example responses or URLs.

Please determine whether the upstream API or response schema changed.

Requirements:
- Make the smallest change necessary to support the current API.
- Preserve backwards compatibility when practical.
- Do not rewrite unrelated parts of JobRadar.
- Add defensive handling for missing/renamed fields.
- Keep existing normalized JobRadar job objects compatible.
- Explain the upstream change you found.
- List the exact files and functions you changed.
- Provide a small test procedure I can run manually.
```

## Prompt for a targeted bug fix

```text
I have a bug in JobRadar.

Expected behavior:
<DESCRIBE EXPECTED BEHAVIOR>

Actual behavior:
<DESCRIBE ACTUAL BEHAVIOR>

Error/log:
<PASTE ERROR>

I am attaching the current relevant JobRadar source files.

Please:
1. identify the root cause,
2. make the smallest targeted fix,
3. preserve existing behavior,
4. avoid unrelated refactoring,
5. handle the relevant edge case defensively,
6. update the displayed JobRadar version if this project uses versioned builds,
7. tell me exactly how to reproduce/test the fix.
```

# Maintainer prompt examples

The [prompt examples](#prompt-examples) above are AI generated. When using an AI different to ChatGPT, it is recommended to start with such a well-formed and detailed prompt.

If the used AI turns out to perform well, more sloppy prompts should also be sufficient. The following examples are real prompts the maintainer has given the ChatGPT AI via the Web-Interface in the browser (german language only!). This should give you an idea about how sloppy prompts can be, that still work.

## Prompt example 1

Prompt for issues with the company watchlist settings implementation.

### Prompt

> das fenster für die settings ist übrigens nicht breit genug für die company watchlist tabelle bzw. ich sehe den vertikalen scrollbalken nicht. er kommt erst, wenn ich das settings-fenster breit genug mache. lässt sich das fixen? desweiteren selektiere ich mehrere einträge und drücke "Detect system" und dann passiert lange nichts. hier wäre ein label äßerst nützlich, vielleicht rechts vom diagnose button, was den aktuellen status anzeigt, also zumindest in form "i/N" wie weit die detection gerade ist

### Response

> Behoben in JobRadar 0.6.9.24.
> 
> Die Company-Watchlist-Tabelle verwendet jetzt ein fest begrenztes Grid-Layout.
Der vertikale Scrollbalken bleibt dadurch auch bei normaler Breite des Settings-Fensters sichtbar.
Der horizontale Scrollbalken befindet sich nun direkt unter der Tabelle und endet vor dem vertikalen Scrollbalken.
Neben Diagnose selected gibt es jetzt ein Statuslabel, zum Beispiel:
>
> Detection: 7/24 — SimScale
>
> Nach Abschluss:
>
> Detection complete: 24/24
>
> Außerdem kann während einer laufenden Erkennung nicht versehentlich noch ein zweiter Detection-Lauf gestartet werden.


## Prompt example 2

A very long sloppy prompt, but fine for the AI. It is generally recommended to use listings for structuring requests in AI prompts.

> ich hätte noch ein paar andere änderungswünsche:
>- wenn der Agent nach jobs sucht, habe ich das gefühl, dass es auf krampf deep-screenings auf jobs macht, wo beim titel schon klar ist dass sie nicht passen, nur weil er vermutlich die anweisung hat mindestens 1-2 rote jobs zu deep-screenen. kann das sein? jedenfalls soll nur dann jobs, die beim shallow screeing mit rot markiert wurden (also als sehr wahrscheinlich unpassend eingestuft wurden), wenn der jobtitel das potential hat, dass sich dahinter doch etwas passendes verbergen könnte. nur dann soll er ein deep-screening machen! aber für alle roten jobs, wo er der meinung ist, da könnte was passenderes dahinter stecken als der erste eindruck vermuten lässt. das ziel ist aber unnötige deep-screenings zu vermeiden!! hier geht es am ende auch um kosten, also geldverschwendung, wenn unnötige screenings gemacht werden. 
>
>
>- wenn möglich sollten die symbole in der ai spalte der haupttabelle via tooltip anzeigen was sie bedeuten; wenn das nicht geht, auch in ordnung.
>
> 
>- wenn man in der job description mit strg+f sucht und man direkt danach nochmal etwas suchen möchte (unabhängig davon ob etwas gefunden wurde oder nicht), dann funktioniert erneutes strg+f nicht mehr, sondern man muss erst ins textfeld klicken. das ist doof und sollte geändert werden. 
>
> 
>- beim list import fenster müsste die source auswahl rechts unten links neben dem Import button sein oder oben drüber, damit man nicht übersieht, dass man hier was einstllen muss 
>- der list import taucht im hauptfenster nicht bei den background ai jobs auf. das fenster sollte auch geschlossen werden können, wobei der job dann im hintergrund weiter läuft. 
>- auch die routen-berechnung sollte in der job-liste stehen, weil da wartet man auch häufig lange und weiß nicht ob da jetzt noch was kommt. falls es fehlerfälle gibt, könnte man das dann mit einem symbol anzeigen (manchmal kommt nämlich nichts)

## Prompt example 3

A very complicated prompt the maintainer himself doesn't understand anymore. But the AI did the exact right thing.

### Prompt:

> noch eine bitte:
>- wenn ich in der liste eine menge jobs selektiere und gemeinsam rejecte und diese dann entfernt werden, dann ist der anfang der zuvor markierten einträge häufig oben außerhabl des sichtbereichs und nach dem entfernen rücken die einträg von unten nach, was bedeutet, dass einträge unterhalb des letzten markierten eintrags der entefernt wurde, nun auch oben außerhalb des bildbereichs ist. das müsste bitte geändert werden: wenn einträge entfernt werden, so dass der nächste nicht-entfernte eintrag oben außerhalb der liste verschwinden würde, dann die scrollposition bitte so anpassen, dass dieser eintrag der erste eintrag im sichtbaren bereich ist. d.h. also es muss wieder so weit hoch gescrollt werden, dass der eintrag oberhalb des zuerst entfernten eintrags gerade außerhalb der tabellenansicht liegt. verstehst du wie ich das meine?

### Response:

> Verstanden und umgesetzt in JobRadar 0.6.9.13.
>
>Nach dem gemeinsamen Reject beziehungsweise Entfernen mehrerer Jobs wird jetzt:
>
>der erste verbleibende Job direkt unterhalb des entfernten Bereichs gesucht,
dieser möglichst als erste sichtbare Tabellenzeile positioniert,
und nur dann auf den vorherigen Job zurückgefallen, wenn unterhalb nichts mehr existiert.
>
>Das gilt für:
>
>Reject selected
>Entfernen über die Delete-Funktion beziehungsweise gemischte gespeicherte und ungespeicherte Einträge
>
>Damit solltest du nach dem Aussortieren genau an der Stelle weiterlesen können, an der der entfernte Block aufgehört hat.
>
>Die Versionsnummer wurde auf 0.6.9.13 aktualisiert.
